# 通用检视准则

## REVIEW-001 问题成立条件

只报告本次变更引入或加重、具有实际影响、具体且可修复的问题。每条问题说明触发输入或操作、执行路径、错误结果、预期行为依据和修复方向。已有问题仅作为上下文；排除需求允许的行为、已经存在的保护和项目明确接受的取舍。不得依赖对作者意图或未提供代码的猜测，不凑问题数，不强制表扬。

证据不足时不要输出确定的 finding；在 summary 中简要写明待确认事实。严重度与置信度分别判断，不得把疑似严重问题降为已确认的一般问题。没有合格问题时 findings 为空。

## REVIEW-002 范围与上下文

以提供的版本和 diff 为依据，只在本次新增或修改行上定位问题；未修改代码只用于证明本次变更的影响。关注删除导致的调用、契约和迁移问题；若删除问题没有可用的新行锚点，在 summary 说明，不伪造行号。

远程 diff 模式只提供本批次变更和来源摘要，不等于完整仓库。不能因 diff 没展示校验、导出或测试就断言它不存在；跨文件问题必须引用实际提供的受影响代码。只有提供了需求、调用方、完整实现或公开项目规范时，才据此核对。不得声称已读取未提供的文件、执行测试、验证全仓或满足所有验收标准。上下文不足和未覆盖范围写入 summary；“未发现明确问题”不等于完整通过。

## REVIEW-003 需求、架构与兼容性

分别考虑需求符合度与代码质量：核对已提供需求的字段、输入输出、流程、失败分支和约束是否落地，是否遗漏行为或引入无关行为。没有需求依据则明确无法核对，不编造需求。

检查模块职责、跨模块私有导入、依赖循环、共享可变状态、进程边界和公开契约。接口两端、运行时校验、持久化格式、数据路径和迁移方案须兼容。项目规范按适用文件范围生效，规范类问题应引用提供的来源及条款；不把某仓库的 i18n 或目录习惯强加给其他仓库。

代码异味只是线索：重复逻辑、误导命名、职责混杂、散落修改、投机抽象和无效中间层只有在能说明具体维护代价或明确规范违例时才报告。尊重隔离、安全和兼容所需的接口，不为减少代码绕过边界。格式、缩进、导入排序等机械检查交给工具，不重复制造风格问题。

## REVIEW-004 正确性、异步与资源

检查空值、空集合、边界、条件、精度、编码、时间和时区；检查幂等、事务、部分失败、回滚、更新或删除范围、数据迁移和缓存失效。检查遗漏 await、Promise 拒绝、fire-and-forget 失败、过期闭包、乱序响应、重复点击、取消和超时；失败后 loading、锁和资源必须正确释放，不得在操作完成前提示成功。

检查 N+1、无界查询、缓存、队列或重试、热点复杂度、主线程阻塞、重复请求，以及连接、流、句柄、监听器、定时器和子进程清理。性能问题必须说明数据规模、调用频率或资源增长条件，不能仅凭“可以并行、缓存或 memo”报告缺陷。

## REVIEW-005 测试与用户体验

检查关键行为、异常、边界、契约和迁移是否有有效验证；修复是否覆盖原始回归场景。测试应调用真实生产逻辑，避免复制实现、过度 mock、弱断言、依赖时序或外部状态、无理由跳过测试或降低门槛。缺少测试时必须指出哪项行为缺少验证；不能仅因未提供测试而认定测试不存在，也不能把缺少测试直接定为 P0。

检查关键操作是否可达、错误反馈是否明确、状态是否真实，以及适用的键盘、无障碍和多语言要求。Electron 重点检查 renderer/preload/main 边界、窄 IPC 接口、输入校验、危险导航、外部链接、文件授权和生命周期。验证建议按风险选择，不默认要求全量构建或 UI 图像验收。

## REVIEW-006 等级与输出复核

- P0：广泛且确定地阻断核心使用或发布，或造成灾难性后果，不依赖臆测的特殊输入，需要立即修复。
- P1：明确且现实可达的条件下导致严重错误、越权、数据损坏、核心功能不可用或严重性能退化，需要优先修复。
- P2：有证据的局部错误、边界回归、兼容问题或实质性规范违例，应正常修复。
- P3：有具体收益、影响较低的维护或体验改善，非阻断建议；纯个人偏好不报告。

高置信度表示代码路径、契约或验证直接支持；中置信度必须列明环境或输入前提；缺少关键事实的低置信度项只写入 summary 的待确认说明。数量不能代替严重度或自动决定是否允许合并。

输出前复核文件和定位、已有保护、真实调用点、规则适用范围、严重度及修复兼容性。同根因去重，独立问题保留。一事一条，标题简明，解释直述触发条件与影响，定位尽量紧凑，不伪造证据、测试结果或规则来源。summary 简述需求依据、已见范围和限制，不等同于批准合并。
